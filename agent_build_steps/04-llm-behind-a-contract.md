# 4. LLM 을 계약 뒤에 세우기

키우는 성질: **판정** · office 데이터: 필요

## 왜

지금 `ask_llm()`은 비어 있지 않은 `### Observed` / `### Inferred` 형식을
검사하고 성공·실패를 구분한다. 그러나 Observed가 증거에 없는 말을 지어냈는지는
형식 검사로 알 수 없다. 다음 과제는 근거 검증과 비용·재개 계약이다.

사람이 결과를 읽는 동안은 이게 괜찮다 — 이상하면 사람이 알아챈다.
**agent 가 이 출력을 다음 단계의 입력으로 쓰는 순간 안 괜찮아진다.**
모델의 헛소리가 검증 없이 파이프라인을 타고 내려간다.

## 개념

**LLM 호출은 네트워크 호출이다.** 파싱하고, 검증하고, 실패를 값으로 다룬다.
"프롬프트를 더 잘 쓰면 된다" 는 검증의 대체물이 아니다. 프롬프트는 성공
확률을 올리고, 검증은 실패를 **보이게** 만든다. 둘 다 필요하다.

계약을 셋으로 나눠 생각하라.

- **형식 계약** — 응답이 정해진 모양인가. 코드가 판정한다. 섹션 두 개가
  있는가, 비어 있지 않은가. 실패하면 재시도 1회, 그래도 실패면 그 디렉터리를
  `describe_failed` 로 ledger 에 남기고 **계속 간다.**
- **근거 계약** — Observed 에 나온 파일 이름이 전부 증거 표에 있는가.
  이건 완벽히는 못 한다. 파일명 대조 정도가 현실적인 천장이고, 그
  천장을 `ponytail:` 주석에 적어라.
- **비용 계약** — 몇 번 불렀고 토큰이 얼마나 갔나. `audit.jsonl` 에 남는다.
  이게 없으면 agent 가 예산을 태우는 걸 사후에도 알 수 없다.

셋 다 **모델 프롬프트가 아니라 코드** 라는 게 요점이다. 모델을 바꿔도
(사내 LLM 이 버전업돼도) 이 셋은 그대로 참이어야 한다.

## 실습

`describe` 동사 안에 검증을 넣는다.

1. 응답에서 두 섹션을 파싱. 없으면 `retry=1`, 그래도 없으면 실패 기록.
2. Observed 안에 나온 `\S+\.\w+` 토큰 중 증거 표의 파일명에 없는 것을
   세어 `unsupported` 로 ledger 에 남긴다. 막지는 말고 세기만 한다.
3. `describe.jsonl` 한 줄 = 한 디렉터리 = `{path, ok, retries, unsupported, raw}`.

**일부러 나쁜 응답 먹이기** (실습의 핵심): `tests/test_spike_fake.py` 의 가짜
LLM 을 셋으로 늘린다 — ① 정상 ② 섹션 없는 산문 ③ 없는 파일명을 지어내는 응답.
셋을 돌리고 `describe.jsonl` 이 각각 `ok=true` / `ok=false` /
`unsupported>0` 으로 나오는지 본다.

여기서 자주 나오는 유혹: ③을 막으려고 프롬프트를 고치고 싶어진다. 고쳐도
된다. 다만 **테스트는 남겨라.** 프롬프트는 모델이 바뀌면 무너지고, 테스트는
그때 소리를 낸다.

## 통과 기준

가짜 LLM 세 종류에 대해 `describe` 가 죽지 않고 끝나며, `describe.jsonl` 이
정상/형식위반/근거없음을 각각 구분해 기록한다.

## 이 단계에서 배워 갈 것

모델 출력에 대한 검증은 프롬프트로 대체되지 않는다. 그리고 검증 실패는
예외가 아니라 **기록되는 값** 이다 — agent 는 한 디렉터리 실패로 멈추면 안 된다.
