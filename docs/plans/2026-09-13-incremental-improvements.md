# 장비 한 대에서 시작하는 단계별 개선

기준은 [아키텍처](../architecture/equipment-data-map.md)와 현재 office 진입점인
[Letter 00](../../equipment-data-parser/00-spike.md)이다. 아래 번호는 개선 순서이며
아키텍처의 rollout 단계 번호와는 다르다.

## 1. Home에서 spike의 판정과 경계 보강

- [x] `list_dirs` 결과를 정규화·검증한 뒤 고정 경로만 `size_dirs`에 전달한다.
  다운로드 직전도 같은 정책으로 검사한다. `ftp_handler/`는 수정하지 않는다.
- [x] 루트 `/`와 정규화 후 중복 루트를 처리한다.
- [x] 파일을 하나씩 통째로 받고 실제 성공 바이트를 집계한다. 조회 크기는
  참고값이며 목표 도달·초과 후 다음 다운로드를 막는다. 전송 실패로 사용량을
  알 수 없으면 `usage_unknown`을 남기고 이후 다운로드를 막는다.
- [x] LLM 시도·유효 형식 응답·실패를 구분한다. 빈 목록이나 LLM 전체 실패는
  성공으로 판정하지 않는다. 형식 검증과 의미 정확성 검토를 구분한다.
- [x] 실행별 출력 디렉터리와 경로 hash 문서명으로 덮어쓰기를 방지한다.
- [x] 금지 요청, 성장 파일, 실패 전송, LLM 오류·형식 위반, 경로 충돌과
  재실행을 가짜 응답으로 검증한다.
- [x] 기존 검사 15개와 신규 회귀 검사 13개, direct·proxy 종단 시나리오
  각각 1개를 통과했다. 종단 검사는 Python 3.11과 로컬 가짜 서버로 실행했다.

검사 명령은 [README](../../README.md)에 있다. 회귀 검사와 로컬 가짜 서버
검사의 통과는 실제 장비에서의 부하·호환성·분석 품질을 증명하지 않는다.

## 2. Office에서 승인된 장비 한 대 확인

Letter 00을 실행한다. 엔지니어가 접속 정보와 좁은 경로를 설정하고 사내 LLM이
proxy 경유 실행 결과를 검토한다. 완료 근거는 해당 letter의 종료 조건과
`problems/00-problems.md`, `equipment-data-parser/progress.md` 기록이다.

확인할 것은 다음과 같다.

- 실제 서버의 목록·SIZE·MDTM 응답과 디렉터리 분류가 맞는가?
- 대표 파일이 디렉터리 용도와 형식을 설명하는 데 충분한가?
- Observed가 근거 범위를 지키고 Inferred가 유용한 추정인가?
- 추가 목록 연결과 파일별 전송의 시간·부하가 허용 가능한가?
- 생략·실패·초과량이 운영자에게 명확히 보이는가?

원본·장비 경로·분석 결과는 사내에 둔다. Home에는 허용된 비식별 요약만
전달한다. Home에서 office 완료 기록을 대신 작성하지 않는다.

## 3. 같은 장비의 반복 실행과 재개

2단계 결과를 근거로 구조화 inventory와 표본·추출 결과 및 근거 hash를 저장한다.
현재의 새 실행 디렉터리는 재개 기능이 아니다. 재개에는 대기 큐, 완료 항목,
누적 요청·바이트 예산, 대상·설정의 정체성이 필요하다. 진행 상태는 아키텍처의
원장·잠금·무결성 규칙을 따른다. 성공한 전체 표본을 보존하고, UTF-8/CP949
문자 중간 절단과 실제로 관측된 형식 차이를 추출 단계에서 검증한다.

통과 조건: 강제 종료 후 재개해도 대기 경로가 누락되지 않고, 완료된 다운로드를
반복하지 않으며, 예산과 사용량 미상 상태가 초기화되지 않는다. 설정이 달라진
실행은 이전 결과를 묵시적으로 재사용하지 않는다.

## 4. 검토된 Data Map에서 Wiki·RAG 생성

구조화 Data Map을 단일 원본으로 삼는다. 메타데이터와 추출 사실, LLM 추론,
미확인을 분리한다. Wiki와 검색 문서는 그 결과에서 파생한다. 답변은 원래
장비 경로와 근거 종류·hash로 연결한다.

통과 조건: 엔지니어가 만든 실제 질문으로 경로·형식·필드 탐색을 검증하고,
표본이 없거나 해석에 실패한 항목을 확정 사실로 답하지 않는다.

## 5. 장비 두 종류 이상으로 확장

두 번째 장비에서 확인된 차이를 profile과 extractor로 분리한다. 새 장비는
별도 rollout으로 실행하고 기존 지도·승인·예산과 섞지 않는다. 관측되지 않은
프로토콜이나 포맷을 위해 미리 추상화를 늘리지 않는다.

통과 조건: 두 장비의 독립 실행과 기존 시나리오 회귀 검사가 통과한다.
스킬 배포의 지원 도구·모델 검증과 운영자 승인 요건은 아키텍처를 따른다.

## 현재 범위와 제한

이번 구현은 1단계다. 2단계의 실제 장비 결과는 아직 기록되지 않았다.
SIZE 실패를 디렉터리 후보로 보는 spike의 한계, 영구 체크포인트 부재,
형식 검증으로 의미 정확성을 보장할 수 없는 점은 남아 있다. 전송 실패 뒤
다시 실행하기 전에는 office 엔지니어가 이전 작업 종료와 사용량을 확인해야
한다. 네트워크 바이트의 엄격한 전송 중 상한은 보장하지 않는다.
